# DriftingLeavesV2 项目优化审查与分步修改计划（核查修订版）

> 审查范围：后端（`Backend/common`、`Backend/entity`、`Backend/server`）、数据库脚本（`sql/`）、四个独立前端工程（`Front-Admin`、`Front-Blog`、`Front-Home`、`Front-Cv`）、Docker/Nginx 部署配置（`DockerForDriftingLeaves/`）及仓库文档（`README.md`、`docs/`）。
>
> 修订说明：本版本结合[优化审查核查报告](./优化审查核查报告.md)对原 42 项问题逐条校准了核查结论、优先级与前置业务约束，修正了汇总计数，并新增 **Redis + Spring Cache 减压方案（`BE-INF-12`）**，明确区分**已复现/已实证缺陷**与**收益待实测项**。
>
> 约束前提：遵守项目 `AGENTS.md` 规范，保持四端完全独立、不跨端共享源码与资源、不通过 `prefers-reduced-motion` 禁用动效；数据库变更遵循存量增量迁移原则，修改锁与缓存逻辑时必须保留既有业务一致性与安全契约。

## 三、Redis + Spring Cache 减压架构设计（针对 `BE-INF-12` / `BE-INF-04` / `BE-INF-05` / `BE-INF-08`）

项目当前已在 [PublicCacheConfig.java](../Backend/server/src/main/java/com/xuan/config/PublicCacheConfig.java) 中接入了基于 Redis 的 Spring Cache（`@EnableCaching(order = 150)`）及 20 个公开只读域（`CacheNames`）。为进一步降低 MySQL 高频读写与大表聚合压力，建议采用**分层缓存策略**，将缓存域清晰划分为两类，而非全部耦合进 `PublicCacheStore` 的写保护阻塞机制：

### 3.1 缓存分层方案

| 缓存类别 | 缓存域 (`CacheNames`) | 对应 MySQL 压力来源 | 推荐 TTL | 失效与一致性策略 |
| --- | --- | --- | --- | --- |
| **A. 强一致公开内容缓存**（沿用 `PublicCacheStore` 版本号+写保护，先修 `BE-INF-05`） | 已有 20 个公开域（`home`、`articles`、`articleDetail`、`categories`、`tags`、`statistics` 等） | 公开站点高频页面与列表查询 | 沿用现有 30s～1h 分级 TTL | 事务内 `beforeMutation` 登记带过期时间的保护令牌；提交后轮换 `generation`；`STATUS_UNKNOWN` 先轮换版本再清理令牌。 |
| **B1. 后台统计报表缓存**（独立 `RedisCacheConfiguration`，标准 Spring Cache） | `adminStats`（实时区间）<br>`adminStatsHistory`（`endDate < 今日 UTC`） | [StatisticsServiceImpl](../Backend/server/src/main/java/com/xuan/service/impl/StatisticsServiceImpl.java#L69-L157) 6 个报表接口对 `blog_page_view`、`blog_visitor`、`blog_article`、`blog_comment`、`blog_message` 的大范围聚合扫描 | `adminStats`: **60s**<br>`adminStatsHistory`: **30m** | 使用标准 `@Cacheable(cacheManager = "redisSimpleCacheManager", ...)`，Key 包含方法名、起止日期、站点码、limit；历史日期数据基本不可变，大幅降低重复翻看报表对 MySQL 的冲击。 |
| **B2. 访客 IP 封禁缓存**（标准 Spring Cache / Redis） | `ipBlock` | [AccessBlockFilter](../Backend/server/src/main/java/com/xuan/filter/AccessBlockFilter.java#L57) 每个非后台 HTTP 请求直查 `blog_visitor` | **60s**（缓存“未封禁”或“已封禁及到期时间戳”） | 后台执行封禁、解封、删除访客事务提交后精确 `@CacheEvict(cacheNames = "ipBlock", key = "#ipDigest")`（或批量失效），保证符合 [API.md](./API.md#L323) 人工封禁实时生效契约；Redis 不可用时按约定回退查库或返回 503。 |
| **B3. 后台权限与菜单授权缓存**（标准 Spring Cache） | `userAuthz` | [AuthorizationProvider](../Backend/server/src/main/java/com/xuan/security/AuthorizationProvider.java#L111) 每次后台请求在拦截器阶段多表查询角色、权限与菜单 | **5m** | Key 为 `userId`；在用户角色变更、角色权限/菜单变更、禁用/删除用户、删除角色事务提交后执行 `@CacheEvict`；**注意**：锁内写操作复核权限（`requireScope`）保持直查数据库，不因缓存放宽写安全边界。 |
| **B4. 文章互动计数短缓存**（可选，需确认实时性契约） | `articleMetrics` | [ArticleServiceImpl.publicArticles](../Backend/server/src/main/java/com/xuan/service/impl/ArticleServiceImpl.java#L119-L152) 列表缓存命中后仍回源查 `publicCounts` 和 `commentNodesByArticles` | **15s～30s** | 评论审核/发布/删除、文章点赞/取消点赞时按 `articleId` 失效；若接口契约要求列表页阅读数/点赞数必须毫秒级强一致，则保留按页批量查询、仅对后台统计与 IP 封禁/鉴权上缓存。 |

### 3.2 Spring Cache 落地关键约束
1. **双 `CacheManager` 隔离**：保留现有 `@Primary` 的 `cacheManager` 给 20 个强一致公开域使用；新增轻量 `simpleCacheManager`（标准 `RedisCacheManager`，支持 `allowNullValues` 或显式哨兵对象防穿透，不经过 `PublicCacheStore` 的 `writers` 阻塞）供 `adminStats`、`ipBlock`、`userAuthz` 使用。
2. **禁止同类自调用失效**：凡使用 `@Cacheable` / `@CacheEvict` 的方法必须通过 Spring 代理调用（或拆到独立支撑组件），避免如 `AuthorizationProvider` 出现自调用绕过 AOP 的问题。
3. **Redis 故障行为明确**：`PublicCacheStore` 维持现有保护策略；`adminStats`、`userAuthz` 缓存读取异常时降级直查数据库并记录告警，不中断后台正常操作。

### Phase 2：Spring Cache + Redis 减压体系建设与缓存稳定性修复
- **目标**：先消除公共缓存永久失效隐患，再通过 Spring Cache + Redis 分层大幅降低 MySQL 高频读与报表聚合压力。
- **包含项**：`BE-INF-05`、`BE-INF-04`、`BE-INF-08`、`BE-INF-12`
- **关键改动**：
  1. 改造 `PublicCacheStore`：`writers` 改为带超时清理的 ZSET，`STATUS_UNKNOWN` 时轮换 `generation` 再移除保护令牌。
  2. 在 `PublicCacheConfig` 中新增轻量 `simpleCacheManager`，为 `StatisticsServiceImpl`（后台 6 个报表接口）、`AccessBlockFilter`（`ipBlock`，写路径精准失效）和 `AuthorizationProvider`（`userAuthz` + 去同类自调用，权限变更时失效、锁内写复核仍直查）接入 Spring Cache + Redis。
  3. 结合接口实时性要求，评估是否启用 `articleMetrics` 短缓存。
- **验收与验证**：
  - 隔离 Redis + MySQL 下验证：事务回滚/异常后缓存自动恢复；封禁/解封 IP 实时生效且命中 Redis 不再查库；角色权限变更后立即失效；后台报表二次请求命中缓存。

### Phase 3：后端并发锁、流式 I/O 与基础设施加固
- **目标**：解除文件大对象入堆与读接口/外部 I/O 长期持锁问题，加固过滤与限流边界。
- **包含项**：`BE-INF-06`、`BE-BIZ-01`、`BE-INF-02`、`BE-INF-03`、`BE-INF-07`、`BE-INF-09`、`BE-INF-10`、`BE-INF-11`
- **关键改动**：
  1. `FileStore`、`AliOssClient`、`FileResponseUtils` 全面流式化，去除 60 MiB `byte[]` 缓冲。
  2. 剥离公开读接口与 `FileServiceImpl.upload` 存储 I/O 的长事务/行锁；按业务一致性边界优化 `SubscriptionNotifier` SMTP 锁内发送。
  3. 修复 `IpUtils` 名称解析回退、`RequestBoundaryFilter` 的 `Content-Length` 预检与数组 `read`、执行器 `InheritableThreadLocal` 隔离与失败审计并发上限，顺带清理热路径重复分配与限流跨维度计数。
- **验收与验证**：
  - `mvn -B -ntp -f Backend/pom.xml verify`；隔离环境回归大文件上传/播放/删除、并发读文章与改状态、超大 JSON 413 拒绝、限流与邮件通知。

### Phase 4：数据库增量迁移、索引优化与 SQL / N+1 治理

- **关键改动**：
