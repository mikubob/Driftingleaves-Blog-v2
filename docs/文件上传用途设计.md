# 文件上传用途设计

文件上传时确定一个用途，保存到 `blog_file.upload_usage`。文件列表和详情随文件资料返回该列，避免为识别用途查询文章正文、封面、头像和音乐等引用。用途表示上传时的选择，换图、移除引用和删除文章都不改写它。未保存关联的上传也会显示所选用途。

| 上传位置 | 保存的用途 |
| --- | --- |
| 文章编辑器的封面上传、正文插图上传 | 分别为 `ARTICLE_COVER`、`ARTICLE_IMAGE` |
| 音乐编辑器的封面、音频、歌词上传 | 分别为 `MUSIC_COVER`、`SONG`、`LYRIC` |
| 账号、用户、主页资料的头像上传 | `AVATAR` |
| 友链头像上传 | `LINK_AVATAR` |
| 经历标志上传 | `EXPERIENCE_LOGO` |
| 社交链接、技能图标上传 | `ICON` |
| 文件管理直接上传，或原客户端未传用途 | 服务端按实际文件类型选择 `IMAGE`、`SONG`、`LYRIC` 或 `ATTACHMENT` |

## 接口与读写

- 普通上传和公开展示图片上传都增加可选 multipart 文本字段 `usage`。各业务入口传固定值。后端先按现有规则识别文件内容，再校验用途是否与文件类型一致。用途码无效或与类型不符时返回 `400/VALIDATION_ERROR`。
- 文件列表、详情和普通上传返回单值 `usage`，并同时返回只含该值的 `usages` 数组。公开展示图片上传继续返回图片地址。
- 列表和详情直接读文件记录中的用途。仅供展示的引用查询和正文扫描已移除。
- `publicImage` 和原有权限检查继续决定访问范围。是否允许删除仍检查实际文章和音乐引用，上传用途仅用于展示。

## 已有数据与部署顺序

1. 备份已有库，在副本核对 [SQL 脚本](../sql/file_upload_usage.sql) 的图片 ID 和引用。固定 ID 映射只适用于 `DriftingLeaves.sql` 对应的数据库，其他库需按各自引用调整映射。空库直接使用[初始化脚本](../sql/drifting_leaves_v2.sql)。
2. 暂停旧版上传，执行迁移并核对脚本末尾的结果。脚本按 MIME 和存储后缀识别歌曲、歌词和图片，再按完整导出中保存的引用填写 7 张图片的具体用途。如果加列后旧版仍接收过上传，在停用旧版上传后从 `START TRANSACTION` 开始补跑回填。
3. 发布后端，再发布管理端并恢复上传。旧管理端省略 `usage` 时使用服务端默认值。
